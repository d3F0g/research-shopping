Read-only inspection of commit `9656f213068ca3a2f566070ed9ca0a64d91d32fe`. No repository edits, credential files, or environment values were read.

## Existing architecture

- `src/server/index.ts:5-7` is the process/environment composition root. `configFromEnvironment` currently reads only API/web ports (`src/server/config.ts:15-16`). `createApp` defaults to fixture providers and receives injectable dependencies (`src/server/app.ts:28-35`). Keep live credentials and Exa adapter composition at this server entrypoint; do not add `VITE_` credential variables or browser Exa calls.
- `/api/turn` validates a strict message/preferences payload, creates a fresh stateless engine, gets a complete turn, adds recorded provider outcomes, and validates the response (`src/server/app.ts:108-117`). `/api/select` independently revalidates catalog identity, evidence, eligibility, and the exact merchant destination (`src/server/app.ts:119-127`, `src/domain/shopping.ts:160-176`). The request logger intentionally records only route/status/timing/outcomes, not queries, source payloads, or provider errors (`src/server/app.ts:21-27,37-54`).
- There is no LLM, system prompt, model SDK, autonomous tool loop, or streaming transport in current `src`/package dependencies. `updatePreferences` is deterministic parsing; answer/ranking are deterministic templates/functions (`src/domain/shopping.ts:25-70,124-154`). `toolActivity` is completed provider outcomes, not reasoning or simulated streaming (`src/domain/contracts.ts:163-170`, `src/client/ResearchResults.tsx:413-463`).

## Boundary that must not receive arbitrary web results

`ResearchProvider.research(product, context): Promise<Claim[]>` (`src/domain/providers.ts:12-14`) is fixture product-claim evidence, not general web research. Its `ClaimSchema` sources are only manufacturer-reference/fixture-observation (`src/domain/contracts.ts:53-87`), and the engine rejects any supported/conflicting source whose URL is not the exact approved product model URL (`src/domain/shopping.ts:104-113`). Client fixture citations repeat this boundary and label timestamps/claims as synthetic (`src/client/ResearchResults.tsx:77-135`). Do not weaken these checks or map arbitrary Exa snippets into `Claim[]`.

Discovery is similarly catalog-bound (`src/domain/shopping.ts:98-101,133-137`, `src/domain/merchant-links.ts:15-19`). Offers require `dataKind: fixture` and sample availability (`src/domain/contracts.ts:102-112`); links must match the catalog model URL (`src/domain/merchant-links.ts:22-37`). Live sources must not alter sample eligibility/ranking/prices/stock/claims/merchant handoff or imply that they substantiate those fixture values.

## App lifecycle and cancellation requirements

- All current session state is React instance state; no server session store (`src/client/App.tsx:75-100`). `runTurn` uses `fetch` with its provided AbortSignal and parses `TurnResponseSchema` (`src/client/api.ts:9-29`). Carry additive source data through this exact parsed response rather than side effects or global caches.
- `cancelWork()` increments both request IDs, aborts both controllers, and clears pending flags (`src/client/App.tsx:112-121`). Edits to preferences and prompt clear results/handoff and invalidate requests (`123-141`). Brand draft edits and invalid budget edits also cancel/clear despite not always incrementing preference revision (`143-176`): merely comparing preference revisions is insufficient.
- `submitTurn` snapshots turn ID, preference revision, and input revision; cancels previous work; clears outcome/selection/errors; then rejects responses if any snapshot is stale (`258-328`). The successful response itself increments preferenceRevision and inputRevision (`301-308`). If source fetching is split into a later request, do not snapshot pre-turn revisions and expect them to remain equal after accepting the turn. Tie it to an accepted outcome generation and clear/cancel it from every existing invalidation path, including retry, brand draft, invalid budget, new prompt, category edits, and reset.
- Product selection has its own controller/ID (`331-360`), and cannot be influenced by web results. Reset cancels work, advances both revisions, and clears all outcome/session state (`363-379`); new source state must be cleared too. A nested `webResearch` field disappears automatically when outcome is cleared, avoiding an extra race-prone state family.
- Current server engine provider AbortSignals are its own per-operation 1.5s deadlines (allowed max 5s), not request AbortSignals (`src/domain/shopping.ts:73-96`). Client abort currently prevents stale UI acceptance; it does not explicitly connect request cancellation to server provider work. The live adapter needs a deliberate server deadline and request abort composition rather than assuming cancellation already propagates end to end.
