# Exa product research verification

Normal development chat uses Exa to discover real products. Research observations, page prices and source links are separate from merchant-verified offers. Missing configuration, disabled research, errors, no evidence and exhausted limits must never return fixture products.

## Automated proof

Run `npm test` for SDK, HTTP, attribution and credit boundaries. Run `npm run test:e2e` for actual Chromium journeys. All automated paths disable billable composition. The offline smoke helper selects `NODE_ENV=test` plus `FIELDNOTE_TEST_FIXTURES=true`; it verifies the legacy fixture regression surface. That helper is not evidence that normal research works.

Research-mode browser cases either inject replies at `/api/turn` or run actual Hono and SDK calls against fake-key loopback provider transport. Record which boundary is exercised and explicitly report simulated provider evidence. Use `tests/e2e/live-research.spec.ts` with the current test titles. The real SDK tests use a local HTTP server and a fake key. No private key is required or copied. A simulated card does not prove that Exa returned that product.

Cover source-backed cards, absent and observed/unverified price text, unknown stock and delivery, concise comparisons, visible supporting excerpts, safe source links and no merchant/purchase controls. Reject forged citation references and quotations missing from their visible source windows. Cover exact full heading and variant identity, scope termination at gaps and competing products, complete sale/list/savings context, wrong-variant and accessory controls, and extraction-independent heading discovery. Preserve exact model and variant attribution, negation and opaque grounding fields. A source-proven product heading can establish an identity-only lead even when native extraction is missing or malformed. Such a lead must disclose that useful specifications were not established. Source-only output is not structured-discovery success.

Test no paid invocation for ordinary replies, presentation changes, disclosures, duplicate IDs, rejected constraints or exhausted quota. Test reservation persistence, shared-path locking and concurrent attempts. Cancellation must reach actual upstream transport before headers and during response-body reads. Browser stop/reset/edit/new-turn checks separately prove that abandoned results cannot publish. Neither proof substitutes for the other.

## Bounded real project check

A real check uses an owned fresh API/web instance, explicit development mode and the existing original root `.env`. Never print the key, put it in command arguments, copy it to another checkout, load it into the browser or upload it to GitHub. Configure one shared absolute `EXA_RESEARCH_LEDGER_PATH`; do not create a fresh allowance for another worktree.

Use the active live allowance explicitly recorded by the orchestrator before dispatch. Earlier proof allowances are historical and do not replenish themselves. Record the permitted calls, conservative reservation, shared ledger, candidate and stop conditions. There are no automatic retries. Stop on unexpected provider errors or charges. Do not spend another live call to prove cancellation when local SDK/HTTP tests establish it.

1. Confirm ownership of both processes and ports. Health must report research mode and configured capability, not fixture mode. Configuration alone does not prove retrieval.
2. Open the real chat in a fresh Playwright browser context. Verify dark first visit and the minimal composer. Count prepare and research `/api/turn` requests separately. Accepting intent adds a local prepare round trip, not a second provider call.
3. Submit one complete research request. Capture the response and actual completed UI. Require real source-linked product observations before claiming discovery. Sources-only or unavailable output remains a recorded limitation.
4. Inspect product identity, exact supporting quotations, returned public HTTPS source URLs, observed-price labels and unresolved constraints. A retrieval timestamp never establishes source freshness, current affordability, stock or delivery.
5. Open evidence and comparisons without sending another research request. Inspect screenshots at desktop 1440px and mobile 390px. Keep the composer usable, citations keyboard-accessible and text within the viewport. Do not open external destinations merely to finish the local check.
6. Within the remaining allowance, use a material follow-up only if needed to establish the feature. Ordinary conversation, detail changes, theme selection and source disclosures must not spend another call. Preserve earlier messages and separate current preferences from historical snapshots.
7. Record reported request cost and sanitized IDs, source count, accepted/rejected observation counts and screenshots. Keep credentials and raw errors out of shared evidence. For a proof run only, opt into the private server diagnostic sink before dispatch. Keep its native extraction and source-structure artifact outside public responses, logs and history, at owner-only permissions and at most 128 KiB. It excludes headers, keys, environment values, cookies and user request fields; truncated content must carry its length and hash. Sink failure cannot retry the operation or alter billing settlement. Inspect the durable ledger without treating it as the remote balance. Stop owned processes and confirm both ports are free.

## Trust and limits

Render source text as text. Source instructions cannot become tools or executable markup. Reject non-HTTPS, credentials, IP literals and local/reserved destinations. A safe URL is not a merchant authorization. Keep the fixture exact-product handoff checks in automated regression; normal research uses View source and has no verified merchant selection.

Independent QA and security pin the actual candidate. Label stubbed browser evidence and real Exa proof separately. Preserve failed attempts with their diagnosis. A passing build, a screenshot or a source count alone does not establish useful research. Report discovery, useful specifications, observed price context and comparison separately. Names alone do not establish a useful specification comparison. Keep unchanged normalized historical captures, authored native candidates and synthetic raw-structure examples distinctly labeled; never reconstruct missing provider output and call it captured evidence. Authorized live merchant proof remains open in Issue #36 and cannot be satisfied by this guide.

## Dynamic product acceptance

Normal product scope uses open descriptions and session criteria, not a finite category or feature registry. Verify an unfamiliar product noun and criterion without source edits. Exercise a complete initial request, contextual criterion editing/removal, budget continuation/skip, natural follow-up and historical response preservation. Request-match, identity, hard criteria and observed-price conditions must remain separately reviewable. Unknown hard fit cannot be promoted through a free generated summary.

The current redesign uses provider-generated source-based comparison and a server-gated conditional choice. Distinguish synthesis, literal supporting quotations and merchant proof. Use explicit returned URL references, not numeric citation-array guesses. Compare exact variants and preserve conflict, negation, currency and conditions. Prices remain observed/unverified and stock remains unverified.

Before release, repeat the three original shopping journeys plus a materially different product class through the actual normal app. Inspect useful distinct alternatives, comparison, justified choice, unknowns, desktop/mobile UI and safe destination behavior. Clearly separate these paid results from API-only prototypes and local synthetic transport. Product failure remains a blocker even when technical checks pass.

## Acknowledged intent and cancellation

Preparation runs the sole server reducer without a provider call. Only the transport response may contain prepared intent; completed history cannot persist it as a finished research result. The client accepts preparation under its current operation generation before starting the one research request. Research has no new message or edit fields.

Test an invalid currency change followed by an ordinary acknowledgment and refresh. The original change must stay pending and research must remain blocked until explicit correction or discard. Preserve unrelated accepted criteria and the original request wording. Test a new hard exclusion accepted before a delayed provider response, then Stop and another comparison. The exclusion must survive Stop and retry. New chat explicitly resets it. Test these with actual Hono and SDK loopback transport, not only route-injected browser responses.
