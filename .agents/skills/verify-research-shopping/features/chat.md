# Conversation and theme

Fieldnote keeps user and assistant messages in one conversation. Contextual questions and shopping content belong inside assistant turns. The composer stays available while history scrolls.

## First visit and theme

Start with a fresh browser context whose operating-system preference is light. Navigate to the owned local app. Require dark tokens on the document before changing any preference. Take a desktop viewport screenshot of the empty chat. Require no permanent filter editor, large request form, empty-results panel or introductory page scroll.

Use the actual theme toggle to choose light mode, refresh and require light mode to remain selected. Capture the rendered light state. Choose dark mode, refresh and require dark mode to remain selected. A fresh independent context must still begin dark. Do not set localStorage directly as proof of the toggle.

## Ordinary messages

Submit a greeting through the composer. Require the submitted message and a truthful assistant reply in the conversation. The reply must remain ordinary text without a product shortlist, preference form or fabricated provider activity.

After a shopping response, submit a brief acknowledgment. Require the original exchange and acknowledgment exchange to remain. Current preferences must remain unchanged, including any unresolved hard constraint. Unknown shopping requirements must still receive an honest clarification instead of being treated as acknowledgments.

## Contextual preferences

In a fresh conversation, submit a useful shopping request without a budget. Require one research request without an optional-budget gate or invented budget. For ambiguous money such as `around $30-40`, require a typed currency question. Inspect its original request, stored bounds and question identity. Answer `SGD` through the composer and require the actual questionId on preparation, retained SGD 30 to 40 bounds and automatic research. The typed answer must bypass another interpretation invocation.

Submit a complete request such as `Wireless headphones for long flights, under S$500`. Require the response to preserve its product description and SGD 500 budget without asking for either again. Inspect the actual turn response as well as the visible preference summary or contextual editor.

Open contextual preference editing only through its visible trigger. Verify a single mounted editor and readable mobile controls. Close it without losing accepted changes or previous messages. The initial screen must not expose this editor permanently.

## Multi-turn results

Capture the first request and response. Then submit `under S$200` through the same composer. Require both user messages and both accepted assistant responses to remain in history. Inspect the second response to require its SGD 200 cap, unchanged relevant hard constraints, and correctly qualified current product observations. Fixture offers apply only to the explicit test composition.

Scope card, comparison, evidence and source controls to the intended assistant message. A historical result is a snapshot. It cannot silently replace the current shortlist or provide an action under obsolete preferences. Opening old evidence must not mutate current accepted preferences.

## Scrolling and composer

Use desktop 1440px and mobile 390px viewports, including a short mobile height. Capture viewport screenshots rather than relying only on full-page images. Read older messages by scrolling the conversation, then return to the latest turn. Require no forced jump while the user reads history.

At both scroll positions, require the composer to remain visible and keyboard-operable. Focus it, enter a multiline message with Shift+Enter, and verify Enter submits once. The composer must not cover an actionable card, disclosure or error. Require no body-level horizontal overflow.

Verify visible keyboard focus, touch-sized actions, readable contrast in both themes and reduced-motion behavior. Screenshots prove rendered appearance only after inspection. Independently judge the result against the chat-first brief; passing existing dashboard tests is insufficient.

## Evidence and limits

Keep actual request/response observations, message retention, theme transitions, scroll/composer measurements, desktop/mobile screenshots, trace, candidate SHA, worktree status and owned-process cleanup. Record exact states covered. In-memory conversation history does not establish refresh, cross-tab or cross-device persistence. Theme persistence is a separate promise.
